Redis 常用数据结构与后端场景

2026/4/19 后端 Redis 缓存 数据结构 高并发

Redis 在后端中的定位

Redis 常用于缓存、计数、限流、分布式锁、排行榜、会话和消息队列等场景。它的优势是内存访问快、数据结构丰富、命令原子性强。

但 Redis 不是数据库的简单替代品。涉及最终一致性、事务、复杂查询和强约束时，仍然要以数据库为准。

String

String 是最常用的数据结构，适合保存简单值。

典型场景：

  • 缓存对象 JSON。
  • 计数器。
  • 分布式锁 value。
  • 验证码。

常用命令：

SET user:1 '{"name":"Tom"}' EX 300
GET user:1
INCR article:1:view_count
SET lock:order:1 uuid NX EX 10

注意点：

  • 缓存对象要设置过期时间。
  • 分布式锁释放时要校验 value，避免误删别人的锁。
  • 大 value 会影响网络传输和内存管理，不适合无限塞 JSON。

Hash

Hash 适合保存对象字段。

HSET user:1 name Tom age 18
HGET user:1 name
HGETALL user:1

适用场景：

  • 用户信息。
  • 商品基础信息。
  • 需要局部更新字段的对象。

Hash 的优势是可以单独更新字段，不需要整体序列化和反序列化。但对象层级复杂时，直接使用 JSON String 可能更简单。

List

List 是有序链表，适合队列、时间线和简单消息缓冲。

LPUSH queue:task task1
RPOP queue:task

如果是可靠消息队列，不建议只靠 Redis List 自己实现。业务可靠性要求高时，应优先选择 RabbitMQ、Kafka 等专用 MQ。

Set

Set 是无序去重集合。

典型场景：

  • 用户标签。
  • 点赞去重。
  • 黑名单。
  • 共同关注。
SADD article:1:likes user1
SISMEMBER article:1:likes user1
SCARD article:1:likes
SINTER user:1:follows user:2:follows

Set 适合表达“是否存在”和“集合关系”。

ZSet

ZSet 是带分数的有序集合。

典型场景：

  • 排行榜。
  • 延迟任务。
  • 滑动窗口限流。
  • 按时间排序的数据。
ZADD rank:score 100 user1
ZREVRANGE rank:score 0 9 WITHSCORES
ZREMRANGEBYSCORE rate:user:1 0 1710000000000

在秒杀限流中，可以用时间戳作为 score，先删除窗口外请求，再统计窗口内请求数。

Bitmap 与 HyperLogLog

Bitmap 适合大量布尔状态，例如签到、是否活跃。

HyperLogLog 适合统计 UV 这类基数，优点是省内存，缺点是有误差。

工程注意点

1. 缓存穿透

查询不存在的数据，导致请求一直打到数据库。可以缓存空值，或使用布隆过滤器。

2. 缓存击穿

热点 key 过期后，大量请求同时打到数据库。可以使用互斥锁、逻辑过期或提前刷新。

3. 缓存雪崩

大量 key 同时过期或 Redis 故障。可以给过期时间加随机值，或做降级和限流。

4. 数据一致性

常见策略是先更新数据库，再删除缓存。极端一致性要求高时，需要结合消息队列、binlog 或延迟双删等方案。

面试表达

可以这样说：

Redis 的价值不只是快，而是数据结构丰富。String 适合缓存和计数，Hash 适合对象字段，Set 适合去重和集合关系，ZSet 适合排行榜和滑动窗口。工程上我会重点考虑过期时间、缓存穿透/击穿/雪崩、热 key、数据一致性和内存占用。
