RabbitMQ 死信队列与补偿链路

2026/4/21 后端 工程化 Java RabbitMQ 消息队列

为什么需要死信队列

在秒杀下单链路中，入口通过 Redis 预扣库存后把消息发到 RabbitMQ，由消费者异步创建订单。如果消费者处理失败，不能简单丢弃消息，否则会出现：

  • Redis 资格已预占，但数据库没有订单。
  • 用户无法再次下单。
  • 失败原因无法追踪。
  • 系统只能靠人工排查日志恢复。

死信队列的作用不是“存放失败消息”这么简单，而是给失败消息提供一个可追踪、可补偿、可人工兜底的恢复入口。

基础配置

1. 定义常量

public static final String SECKILL_EXCHANGE = "seckill.order.exchange";
public static final String SECKILL_QUEUE = "seckill.order.queue";
public static final String SECKILL_ROUTING_KEY = "seckill.order.create";

public static final String SECKILL_DLX = "seckill.order.dlx";
public static final String SECKILL_DEAD_QUEUE = "seckill.order.dead.queue";
public static final String SECKILL_DEAD_ROUTING_KEY = "seckill.order.dead";

命名要能表达业务含义，避免只叫 queue1、deadQueue。后续排查消息堆积时，清晰命名能明显降低定位成本。

2. 给业务队列绑定死信交换机

@Bean
public Queue seckillQueue() {
    return QueueBuilder.durable(SECKILL_QUEUE)
            .withArgument("x-dead-letter-exchange", SECKILL_DLX)
            .withArgument("x-dead-letter-routing-key", SECKILL_DEAD_ROUTING_KEY)
            .build();
}

这里的两个参数是 RabbitMQ 约定：

  • x-dead-letter-exchange：消息变成死信后转发到哪个交换机。
  • x-dead-letter-routing-key：死信转发时使用的 routing key。

3. 新增死信交换机、队列和绑定关系

@Bean
public DirectExchange seckillDeadLetterExchange() {
    return new DirectExchange(SECKILL_DLX, true, false);
}

@Bean
public Queue seckillDeadLetterQueue() {
    return QueueBuilder.durable(SECKILL_DEAD_QUEUE).build();
}

@Bean
public Binding seckillDeadLetterBinding() {
    return BindingBuilder.bind(seckillDeadLetterQueue())
            .to(seckillDeadLetterExchange())
            .with(SECKILL_DEAD_ROUTING_KEY);
}

交换机和队列都应该持久化，避免 Broker 重启后基础设施丢失。

消费失败处理策略

消费者不要无限重试，否则会造成消息反复入队、阻塞正常消息。更稳妥的做法是限制重试次数，并把最终失败的消息转入死信队列。

try {
    orderService.createOrder(message);
    channel.basicAck(deliveryTag, false);
} catch (RetryableException e) {
    channel.basicNack(deliveryTag, false, true);
} catch (Exception e) {
    failureLogService.markPending(message, e);
    channel.basicReject(deliveryTag, false);
}

关键点：

  • 可重试异常可以 basicNack(..., requeue=true)。
  • 不可重试或超过次数后 basicReject(..., requeue=false)，让消息进入死信队列。
  • 进入死信前先落失败日志，确保消息具备业务维度的追踪记录。

死信补偿流程

死信消费者拿到消息后，不应该直接再次盲目下单，而是先检查系统当前状态。

死信消息
  ↓
查询订单是否已存在
  ├─ 已存在：标记 SUCCESS
  ↓
尝试补单
  ├─ 成功：标记 RETRIED_SUCCESS
  ↓
回滚 Redis 预占
  ├─ 成功：标记 ROLLED_BACK
  ↓
人工介入：标记 MANUAL_REVIEW

状态流转建议固定下来，便于后续做后台页面或运维脚本。

状态 含义 后续动作
PENDING 消息失败，等待死信处理 死信消费者接管
SUCCESS 订单实际已成功 无需补偿
RETRIED_SUCCESS 补单成功 关闭失败单
ROLLED_BACK 已释放 Redis 预占 用户可重新尝试
MANUAL_REVIEW 自动恢复失败 人工核查

面试表达重点

回答死信队列时，不要只背配置。更好的表达是：

我在业务队列上绑定死信交换机，消费者失败后按异常类型决定是否重试。超过重试次数的消息会进入死信队列，死信消费者先检查订单是否已经成功，再尝试补单；补单失败则回滚 Redis 预占，最后仍失败就进入人工复核状态。这样失败消息不会静默丢失，并且能形成可追踪、可补偿、可兜底的闭环。

后续可增强点

  • 生产者 confirm，保证消息成功到达 Broker。
  • 本地消息表，处理“业务成功但消息发送失败”的场景。
  • 消费重试次数写入消息 header 或失败日志，避免无限重试。
  • 给死信积压配置告警，避免补偿链路失效后无人发现。
