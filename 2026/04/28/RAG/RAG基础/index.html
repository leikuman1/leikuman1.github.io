RAG 基础：从检索增强到可上线问答

2026/4/28 AI应用 RAG Embedding 向量检索 后端

RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把“外部知识检索”和“大模型生成”结合起来的方案。

简单说：先从知识库里找资料，再让大模型基于资料回答问题。

它解决的核心问题是：

  • 大模型本身不知道企业私有数据。
  • 模型参数知识可能过期。
  • 直接让模型回答容易幻觉。
  • 用户需要知道答案来源，方便验证。

RAG 的价值不是让模型“更聪明”，而是让模型能使用可更新、可追溯的外部知识。

核心流程

RAG 主要分为离线建库和在线问答两部分。

离线建库

原始文档
  ↓
解析和清洗
  ↓
文本切分
  ↓
生成 Embedding
  ↓
写入向量索引

常见输入包括 PDF、网页、Word、数据库记录、接口文档和 FAQ。工程上要先做清洗，去掉目录、页眉页脚、重复内容和无意义噪声。

文本切分是关键步骤。切得太大，检索命中不精准；切得太小，上下文不完整。比较稳妥的方式是优先按标题、段落、列表和表格结构切分，再用 token 长度做兜底。

在线问答

用户问题
  ↓
问题向量化
  ↓
检索 top-k 文档片段
  ↓
可选 rerank
  ↓
构造 Prompt
  ↓
LLM 生成答案
  ↓
返回答案 + 引用来源

这里最重要的是“答案必须能追溯来源”。如果只返回一段看起来正确的回答，却没有文档来源，用户很难判断可信度。

Embedding 和向量检索

Embedding 可以理解为文本的语义坐标。

例如：

  • “苹果手机怎么截图？”
  • “iPhone 如何截屏？”

这两句话字面不同，但语义接近。Embedding 模型会把它们映射成距离较近的向量。

检索时，系统把用户问题也转成向量，然后和知识库中的 chunk 向量计算相似度。常见指标是余弦相似度：

cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)

余弦相似度关注两个向量方向是否接近。方向越接近，通常表示语义越相似。

工程上容易踩坑的点

1. 检索不到不等于模型不会答

如果 Prompt 没有限制，模型可能在检索结果不足时继续编答案。因此 Prompt 里要明确要求：上下文不足时说明无法确定。

2. top-k 不是越大越好

top-k 太小可能漏掉关键资料，太大又会引入噪声，甚至挤占上下文窗口。实际需要根据文档质量和问题类型调参。

3. chunk 需要带元数据

每个 chunk 至少应该保留：

  • 文档标题。
  • 来源 URL 或文件名。
  • 页码或段落位置。
  • 更新时间。
  • 权限信息。

这些元数据决定了能否返回可靠引用，也决定了后续能否做权限过滤。

4. RAG 也需要评估集

不能只凭主观感觉判断效果。至少要准备一批典型问题，检查：

  • 是否检索到正确资料。
  • 回答是否基于上下文。
  • 引用来源是否准确。
  • 改写问法后结果是否稳定。
  • 上下文不足时是否拒答。

面试表达

可以这样概括：

RAG 的核心是先把文档解析、清洗、切分并向量化，建立可检索知识库；用户提问时先检索相关 chunk，再把检索结果和问题一起放进 Prompt，让大模型基于上下文生成答案。工程上我会重点关注切分策略、检索相关性、引用来源、权限过滤和拒答机制，因为这些决定了 RAG 系统是否可信、可维护。

总结

RAG 不是简单的“向量数据库 + 大模型”。它是一条完整的数据链路：

  • 文档要干净。
  • chunk 要合理。
  • 检索要相关。
  • Prompt 要约束。
  • 答案要有来源。
  • 失败要能降级。

这些才是 RAG 从 Demo 走向可用系统的关键。
