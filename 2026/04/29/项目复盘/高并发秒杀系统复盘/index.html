高并发秒杀系统复盘

2026/4/29 项目复盘 工程化 后端 Redis 高并发 RabbitMQ Lua

项目背景

这个项目模拟优惠券秒杀场景：大量用户在短时间内同时请求下单。核心挑战不是完成一个下单接口，而是让系统在高并发下仍然能保证：

  • 不超卖。
  • 同一用户不能重复下单。
  • 数据库写入压力可控。
  • 异步消息失败后有可追踪、可补偿、可兜底的恢复链路。

我主要负责下单链路的设计和优化，重点围绕 Redis 原子校验、RabbitMQ 削峰、数据库幂等和死信补偿展开。

总体链路

用户请求
  ↓
接口层限流与参数校验
  ↓
Redis + Lua 原子判断库存和一人一单
  ↓
发送下单消息到 RabbitMQ
  ↓
消费者异步创建订单
  ↓
MySQL 落库 + 唯一索引兜底
  ↓
失败消息进入死信/补偿链路

入口只做快速校验和资格预占，真正落库放到异步消费者中处理。这样可以把瞬时流量从数据库前移到 Redis 和 MQ，降低数据库被直接打穿的风险。

关键设计

1. Redis + Lua 做原子资格校验

Lua 脚本主要做四件事：

  1. 根据 voucherId 组装库存 key 和已下单用户集合 key。
  2. 读取库存，库存不足直接返回失败。
  3. 判断当前用户是否已经抢过该券，已存在则返回重复下单。
  4. 校验通过后扣减 Redis 库存，并把 userId 写入用户集合。

这几步放到 Lua 中执行，是为了保证 Redis 内部操作的原子性，避免并发请求在“判断库存”和“扣减库存”之间穿插执行。

需要说明边界：Redis 预扣只代表用户拿到了下单资格，不代表订单最终成功。最终成功仍以 MySQL 订单落库为准。

2. 用户维度滑动窗口限流

限流按用户维度做，而不是只做全局限流。原因是这个场景主要要拦截同一用户的重复点击、脚本刷接口和网络抖动导致的重复提交。

如果只做全局限流，少数异常用户可能影响其他正常用户；用户维度限流更精准。

实现上使用 Redis ZSet + Lua：

  • score 使用请求时间戳。
  • 每次请求先清理窗口外数据。
  • 判断窗口内请求数是否超过阈值。
  • 写入本次请求记录，并给 key 设置略大于窗口的过期时间。

这个方案有内存成本，但窗口很小、阈值低、过期及时，因此单用户 ZSet 数据量可控。

3. RabbitMQ 削峰与解耦

入口拿到资格后，不直接同步写数据库，而是投递下单消息。消费者异步执行数据库落库。

这样做的收益：

  • 接口响应更快。
  • 数据库承受的是 MQ 平滑后的流量。
  • 下单逻辑可以独立扩展消费者数量。

代价是系统从强同步变成最终一致，必须补充消息失败处理、订单幂等和 Redis 预占回滚。

4. 数据库唯一索引兜底

Redis + Lua 解决入口并发，但数据库仍然要有最终兜底。例如对 voucher_id + user_id 建唯一索引，防止极端情况下重复订单落库。

这是面试中需要强调的点：不能只依赖缓存层判断，数据库约束才是最终一致性的最后防线。

死信与补偿策略

正常消费者第一次失败时，可以先 NACK + requeue=true，允许消息再消费一次。如果仍然失败，就记录一条 PENDING 状态的失败日志，然后 basicReject(requeue=false)，让消息进入死信队列。

死信消费者处理逻辑：

  1. 先查订单是否已经落库成功。
  2. 如果已经成功，将失败日志标记为 SUCCESS。
  3. 如果未成功，尝试重新执行补单逻辑。
  4. 补单成功，标记为 RETRIED_SUCCESS。
  5. 补单仍失败，回滚 Redis 预占库存和用户资格。
  6. 回滚成功，标记为 ROLLED_BACK。
  7. 回滚失败，标记为 MANUAL_REVIEW，交给人工处理。

这条链路的核心目标是：失败消息不能静默丢失，必须可追踪、可恢复、可兜底。

面试官可能追问

为什么不用 synchronized 或本地锁？

本地锁只能控制单 JVM 内部并发，多实例部署时无法保证全局互斥。秒杀资格判断涉及全局库存和用户资格，应该放到 Redis 这类集中式组件中处理。

Redis 扣了库存但数据库落库失败怎么办？

这就是异步链路必须补偿的原因。失败后通过死信队列和补偿任务检查订单状态，如果无法补单成功，就回滚 Redis 预扣库存和用户资格，必要时进入人工复核。

MQ 会不会丢消息？

需要从生产端确认、交换机和队列持久化、消费者 ACK、死信队列、失败日志几个层面保证。项目里重点做了消费者失败后的死信补偿；如果继续增强，可以补生产端 confirm 和消息表。

Lua 脚本能不能完全防超卖？

只能保证 Redis 内部资格预扣不超卖。最终订单是否超卖还需要数据库约束、消费者幂等和补偿逻辑共同保证。

项目收获

这类项目的重点不是“用了哪些中间件”，而是能不能把并发、异步、幂等和一致性串成闭环。我的理解是：

  • Redis 解决入口高并发判断。
  • MQ 解决削峰和解耦。
  • MySQL 解决最终数据约束。
  • 死信和补偿解决失败恢复。
  • 日志和状态机解决可观测与人工介入。
