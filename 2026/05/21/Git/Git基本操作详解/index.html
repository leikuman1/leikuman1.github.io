Git 基本操作详解：merge、rebase 与团队协作

2026/5/21 工程化 Git 团队协作 merge rebase

推荐练习工具

新手理解 Git 分支模型，可以先用 LearnGitBranching 练习。它能把 commit、branch、merge、rebase 的变化可视化。

git pull 的本质

默认情况下：

git pull = git fetch + git merge

fetch 负责从远程拿最新提交，但不改本地工作分支；merge 负责把远程提交合并进当前分支。

更稳妥的团队操作是：

git fetch origin
git diff HEAD origin/main
git merge origin/main

这样可以先看远程改了什么，再决定是否合并。

本地分支和远程跟踪分支

main 和 origin/main 不是同一个分支：

  • main：本地分支。
  • origin/main：本地记录的远程 main 最新状态。

执行 git fetch origin 后，更新的是 origin/main。如果要把远程 main 合进当前分支，需要执行：

git merge origin/main

merge

merge 的作用是把另一个分支的提交合并到当前分支。

git merge main

假设当前在 member1 分支：

A --- B --- C        main
      \
       D --- E      member1

执行 git merge main 后：

A --- B --- C        main
      \       \
       D --- E --- M member1

M 是一次 merge commit，它有两个父提交。merge 的优点是保留真实分叉历史，缺点是提交记录可能变复杂。

fast-forward merge

如果当前分支没有自己的新增提交，只是落后于 main：

A --- B --- C --- D    main
      ^
      member1

执行 merge 后，Git 只需要把 member1 指针移动到 D：

A --- B --- C --- D    main
                  ^
                  member1

这叫 fast-forward merge，不会产生额外 merge commit。

rebase

rebase 可以理解为：把当前分支自己的提交“重新放到目标分支最新提交后面”。

git rebase main

原始结构：

A --- B --- C        main
      \
       D --- E      member1

执行 rebase 后：

A --- B --- C --- D' --- E'   member1
            ^
            main

注意 D'、E' 是新提交，不是原来的提交。rebase 会改写提交历史。

merge 和 rebase 怎么选

场景 推荐
公共分支合并功能分支 merge
个人分支提交 PR 前整理历史 rebase
分支已经推给多人共同使用 不要随便 rebase
想保留真实协作历史 merge
想让个人分支历史更线性 rebase

我的习惯：

  1. 开发时在个人分支提交。
  2. 提 PR 前先同步最新 main。
  3. 如果只是个人分支，必要时用 rebase 整理。
  4. 公共分支合并用 merge 或平台默认策略。

面试表达

可以这样说：

pull 本质上是 fetch 加 merge。团队协作中我更倾向先 fetch，再 diff 远程分支，确认变化后再 merge。merge 会保留真实分叉历史，rebase 会改写提交让历史更线性。rebase 适合整理个人分支，不适合随便改写多人共享分支。
