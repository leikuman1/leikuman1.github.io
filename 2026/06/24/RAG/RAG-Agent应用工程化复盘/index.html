RAG/Agent 应用工程化复盘

2026/6/24 AI应用 工程化 RAG 后端 Agent

背景

AI 应用不能只停留在“调用一个大模型接口”。真正落地时，常见问题包括：

  • 模型不知道私有知识。
  • 回答没有来源，无法验证。
  • 用户问题不稳定，容易触发错误流程。
  • Agent 自主性过强，生产环境难以控制。
  • 失败时缺少日志、重试和降级策略。

因此我更倾向于把 AI 应用当成后端系统来设计：输入校验、数据检索、模型调用、结果验证、日志记录、异常处理都要有明确边界。

RAG 链路设计

文档导入
  ↓
解析清洗
  ↓
文本切分
  ↓
Embedding
  ↓
向量索引
  ↓
用户提问
  ↓
检索 + 可选重排
  ↓
构造 Prompt
  ↓
模型生成
  ↓
返回答案和来源

RAG 的核心价值是让模型基于外部资料回答，而不是只靠参数记忆。工程上最重要的不是“用了向量数据库”，而是检索结果是否可信、上下文是否组织合理、答案是否能追溯来源。

关键工程取舍

1. 文档切分不能只按固定长度

固定 token 长度容易切断语义。更合理的策略是优先按标题、段落、列表、表格等结构切分，再设置最大长度兜底。

切得太大，检索命中不精准；切得太小，上下文不完整。实际项目中需要用问答样例反复评估。

2. 返回来源比“回答更像人”更重要

面向知识库问答时，答案必须附带来源，例如文档标题、页码、URL 或 chunk id。否则模型即使回答正确，用户也很难信任。

3. Prompt 要约束模型边界

Prompt 中需要明确：

  • 只能基于给定上下文回答。
  • 上下文不足时说明不知道。
  • 不要编造不存在的引用。
  • 输出结构要稳定，方便前端渲染或后续解析。

4. Agent 适合放在可控节点

Agent 的优势是能规划和调用工具，但生产环境不能让它无限自主执行。更稳妥的方式是：

  • 用 Workflow 固定主流程。
  • 在分类、路由、总结、工具选择等节点使用 LLM。
  • 对写操作和外部副作用加确认或审批。
  • 给每一步记录输入、输出和工具调用日志。

一个可讲的应用形态

可以设计一个“站内知识助手”：

  1. 用户问博客里的技术问题。
  2. 系统先检索相关文章 chunk。
  3. RAG 生成带来源的回答。
  4. 如果用户要求进一步整理，Agent 再调用工具生成学习路线或面试提纲。
  5. 对任何需要修改文件、发送消息、部署的动作都要求人工确认。

这个设计能同时体现 AI 应用能力和后端工程能力：既理解 RAG/Agent，也知道生产环境需要边界。

面试官可能追问

RAG 能完全解决幻觉吗？

不能。RAG 只能降低幻觉概率。检索不到、检索错、上下文太长、Prompt 约束不足，都可能导致错误回答。因此必须返回来源，并在上下文不足时允许模型回答“不确定”。

向量数据库是不是必须的？

不是。小规模文档可以用本地向量索引甚至关键词检索。向量数据库更适合数据量增长、需要过滤、权限隔离和在线更新的场景。

Agent 和 Workflow 怎么选？

流程确定、可预期、对稳定性要求高，用 Workflow。任务开放、需要动态判断和工具选择，可以嵌入 Agent。我的倾向是生产环境用 Workflow 控主流程，在局部节点使用 Agent 能力。

如何评估 RAG 效果？

至少准备一组测试问题，观察：

  • 是否检索到正确文档。
  • 答案是否基于上下文。
  • 来源是否准确。
  • 上下文不足时是否会拒答或说明不确定。
  • 不同问法下结果是否稳定。

总结

RAG 和 Agent 项目的面试表达重点不是“我调了某个模型”，而是：

  • 数据怎么进入系统。
  • 检索怎么保证相关性。
  • 回答怎么保证可追溯。
  • Agent 怎么控制副作用。
  • 失败怎么记录、降级和复盘。

这和传统后端项目的思路一致：明确边界、控制风险、保留证据、持续迭代。
