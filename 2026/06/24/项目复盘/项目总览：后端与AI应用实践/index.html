项目总览：后端与 AI 应用实践

2026/6/24 项目复盘 工程化 后端 AI应用

为什么写这篇

这篇文章是博客的项目入口，用来把零散的学习笔记收敛成面试官容易理解的能力地图。我的重点不是“会用某个框架”，而是能把业务问题拆成可实现、可验证、可维护的工程方案。

当前重点项目

项目方向 解决的问题 体现的能力
高并发秒杀下单 超卖、重复下单、数据库写入压力、消息失败补偿 Redis + Lua、RabbitMQ、幂等、最终一致性
RAG/Agent 应用 私有知识问答、来源可追溯、工具调用和流程可控 检索增强、Prompt 组织、Workflow、Agent 边界
FastAPI 后端服务 快速构建接口、参数校验、异常处理、数据库访问 Web API 设计、Pydantic、ORM、错误处理
Go 并发基础 goroutine 协作、channel、锁与等待机制 并发模型、阻塞分析、资源控制
Git 团队协作 分支同步、merge/rebase、PR 前整理 工程协作、提交历史治理、冲突处理

  3. RAG 基础 和 什么是 Agent：补充 AI 应用底层概念。

面试表达主线

1. 先讲业务压力，再讲技术方案

例如秒杀项目不能直接说“我用了 Redis 和 RabbitMQ”，而应该先说明问题：

  • 同一张券瞬时并发抢购，直接打数据库容易超卖。
  • 用户重复点击或脚本请求会导致重复下单。
  • 下单链路同步写库会放大数据库压力。
  • MQ 消息失败后必须能追踪、重试、补偿和兜底。

技术方案只是这些问题的响应：Redis + Lua 解决入口原子校验，RabbitMQ 做削峰，数据库唯一索引做最终幂等，死信队列处理失败闭环。

2. 方案要能讲边界

我会重点说明每个方案的边界：

  • Redis 预扣库存不是最终成功，最终结果仍以订单落库为准。
  • Lua 能保证 Redis 内部操作原子性，但不能覆盖数据库侧失败。
  • MQ 削峰提升稳定性，但引入最终一致性和补偿复杂度。
  • RAG 能减少幻觉，但检索质量、分块策略和引用来源仍决定效果上限。
  • Agent 能提高自动化程度，但生产环境通常要用 Workflow 固定主流程，避免不可控自主行为。

3. 复盘要落到可维护性

我更关注这些细节：

  • 错误是否可观测：失败状态、日志、消息 ID、订单 ID 是否能追踪。
  • 失败是否可恢复：重试、回滚、人工介入是否有明确状态。
  • 数据是否有兜底：Redis、MQ、DB 三者之间是否有最终一致性策略。
  • 代码是否容易接手：职责拆分、命名、异常处理和关键注释是否清楚。
