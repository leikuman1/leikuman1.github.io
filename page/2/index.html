面试官您好，我这个项目是一个基于 Spring Boot、Redis、RabbitMQ 和 MySQL 实现的高并发秒杀下单项目，主要模拟优惠券秒杀这种瞬时高并发场景。我主要负责的是下单链路这一块的设计和优化，重点解决高并发下的超卖、重复下单、数据库写入压力过大，以及异步链路下的数据一致性问题。

在实现上，我先用 Redis + Lua 做秒杀资格的原子校验，把库存判断、一人一单和库存预扣放到一个脚本里执行；然后在入口前增加了基于 Redis ZSet + Lua 的滑动窗口限流，控制单用户请求频率；通过 RabbitMQ 把下单请求异步化，削峰解耦，减轻数据库并发压力；另外我还补了死信队列和补偿逻辑，对下单失败的消息做重试、回滚 Redis 预占和人工介入标记，尽量保证最终一致性。除此之外，我还做了售罄快速失败和 JVM 调优，用来减少无效请求开销并提升压测下的稳定性。

这个 Lua 脚本主要做四件事。
第一，先根据 voucherId 组装 Redis key，一个是库存 key，一个是下单记录 key。
第二，读取库存，如果库存小于等于 0，就直接返回失败，表示库存不足。
第三，检查当前用户是否已经在这个券对应的下单用户集合里，如果已经存在，就返回失败，表示重复下单。
第四，如果前两步都通过，就在 Redis 里先执行库存预扣减，再把 userId 写入这个券对应的下单用户集合里，表示这个用户已经占到了购买资格。整个过程放在 Lua 里执行，是为了保证这几步操作的原子性，避免高并发下出现超卖或者一人多单。

“正常消费者第一次消费失败时，我会先 NACK + requeue=true，允许消息再消费一次。
如果第二次还是失败，就先记录一条 PENDING 状态的死信日志，然后 basicReject(requeue=false)，让消息自动进入死信队列。

死信消费者收到消息后，会先查这笔订单是否其实已经落库成功了，如果已经成功，就直接把死信日志标记成 SUCCESS。
如果还没成功，就再尝试补单一次，也就是重新走数据库侧的下单逻辑；如果这次补单成功，就标记成 RETRIED_SUCCESS。
如果补单还是失败，就继续执行 Redis 预占回滚，把之前 Lua 里预扣的库存和用户资格释放掉；如果回滚成功，就标记成 ROLLED_BACK。
如果连回滚也失败，说明这条消息已经不能自动恢复了，就把它标记成 MANUAL_REVIEW，后续交给人工介入处理。
所以这条死信链路的核心目标是让失败消息具备可追踪、可补偿、可兜底的闭环能力。”

如果只看单个用户的 ZSet，在我的场景里窗口很小，而且限制是每秒最多 1 次请求，所以正常情况下一个用户在窗口内只会留下很少几条记录，很多时候甚至只有 1 条，因此单个 ZSet 的数据量其实不大。

但如果从整体看，用户规模很大时，还是会有比较多的 key 和对象元数据开销，所以不能说完全没有内存成本。
因此我的处理思路是：一方面通过 ZREMRANGEBYSCORE 及时清理窗口外请求，另一方面给这个限流 key 设置一个略大于窗口时间的过期时间，让不活跃用户的 ZSet 自动过期回收。这样就能把内存占用控制在一个比较可接受的范围内。

所以结论不是 ZSet 完全不占内存，而是对于我这个‘小窗口、低阈值、及时清理、带过期时间’的限流场景，它的内存开销是可控的。”

“因为这个限流主要是为了拦截单个用户在极短时间内的重复请求，所以我按用户维度做限流，而不是做全局限流。
如果只做全局限流，那高峰期可能会因为少数用户的高频请求把整个接口限住，反而影响其他正常用户的秒杀体验；而按用户维度限流，可以更精准地约束异常频繁点击、脚本刷接口或者网络抖动下的重复提交。

另外，这个项目本身还有‘一人一单’的业务约束，但那是资格校验层解决的问题，是通过 Redis + Lua 和数据库幂等兜底来保证的。
限流和一人一单虽然都和用户有关，但本质上是两层不同的控制：
前者是流量保护，后者是业务约束

RAG基础
RAG 2026/4/28

RAG是什么

RAG（Retrieval-Augmented Generation）是一种结合了检索和生成的自然语言处理技术。

RAG的工作流程

RAG主要干两件事情，离线建库和在线问答

离线建库: 把资料变成可检索知识库

原始文档
↓
文档清洗/解析
↓
切分成 chunks
↓
生成向量 embeddings
↓
存入向量数据库/检索索引

常见步骤：

收集数据
例如 PDF、网页、Word、数据库记录、内部文档、FAQ 等。

解析和清洗
去掉无关内容，提取正文、标题、表格、元数据等。

切分文本
把长文档切成较小片段，比如每段 300 到 1000 tokens。
切太大，检索不精准；切太小，上下文不完整。

向量化
用 embedding 模型把每个文本片段转成向量。

建立索引
把文本片段、向量、来源信息一起存到向量数据库，比如 FAISS、Milvus、 等。

在线问答：用户提问时检索相关资料塞入prompt再调用llm回答

用户问题
↓
问题向量化
↓
检索相关 chunks
↓
可选：重排序 rerank
↓
把检索结果塞进 prompt
↓
LLM 生成答案
↓
返回答案 + 引用来源

常见步骤：

用户输入问题

对问题做 embedding
把问题也转成向量。

相似度检索
在向量库里找最相近的文档片段。

重排序
可选，用 reranker 模型把候选结果重新排序，提高相关性。

构造 Prompt
把检索到的资料作为上下文，连同用户问题一起发给大模型。

生成答案
大模型基于检索内容回答，而不是只靠自己记忆。

返回引用
最好附上来源文档、页码、URL 或 chunk ID，方便用户验证。

RAG的作用

RAG = 先从知识库里找资料，再让大模型基于这些资料回答问题。
rag的核心价值是：让模型能使用外部知识、减少幻觉、支持私有数据、并且知识库可以持续更新。

向量与向量夹角的余弦

上过高中应该都知道向量是什么，向量是有大小和方向的量，可以用来表示空间中的点、线、面等几何对象，也可以用来表示物理量如速度、力等。

在rag里，向量可以理解为文本的语义坐标。比如两句话：

苹果手机怎么截图？
iPhone 如何截屏？
字面不完全一样，但意思很接近。Embedding 模型会把它们转成一串数字，例如：

[0.12, -0.03, 0.88, 0.41, …]
这串数字就是向量 embedding。真正的 embedding 通常有几百到几千维。

向量的基本概念

在 RAG 中，向量主要用于表示语义：

文本 chunk → embedding 模型 → 向量
用户问题 → embedding 模型 → 向量
然后系统比较“问题向量”和“文档片段向量”之间的距离或相似度，找出最相关的内容。

可以把向量想象成地图上的点：

意思相近的文本 → 在向量空间里距离近
意思无关的文本 → 在向量空间里距离远
例如：

“如何重置密码”
“忘记密码怎么办”
向量会比较接近。

而：

“如何重置密码”
“北京明天天气”
向量就会比较远。

余弦相似度

余弦相似度用来衡量两个向量的“方向是否接近”。

它不太关心向量有多长，更关心两个向量指向的方向是不是一致。

公式是：

cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)
其中：

A · B 表示两个向量的点积
||A|| 表示向量 A 的长度
||B|| 表示向量 B 的长度
结果通常在 -1 到 1 之间：

1 表示方向完全相同，语义非常接近
0 表示基本无关
-1 表示方向完全相反

这其实就是高中立体几何里向量夹角余弦公式，一般拿来求二面角或异面直线夹角
在很多文本 embedding 场景里，实际常见结果更多是 0 到 1 附近。

举个二维小例子

假设有两个向量：

A = [1, 2]
B = [2, 4]
先算点积：

A · B = 1×2 + 2×4 = 10
再算长度：

||A|| = sqrt(1² + 2²) = sqrt(5)
||B|| = sqrt(2² + 4²) = sqrt(20)
代入公式：

cos(A, B) = 10 / (sqrt(5) × sqrt(20))
= 10 / 10
= 1
所以它们方向完全一致，相似度是 1。

虽然 B 比 A 长，但他们是平行向量，方向一样，所以余弦相似度认为它们非常相似。
RAG 检索时大概是这样：

用户问题：怎么修改登录密码？
↓
转成问题向量 Q
↓
拿 Q 和知识库中每个 chunk 的向量比较
↓
用余弦相似度排序
↓
取 top-k 个最相似的 chunk
↓
交给大模型生成答案

总结

向量 = 文本语义的数字表达
余弦相似度 = 判断两个语义向量方向有多接近的方法
在 RAG 中，它们共同完成的事情是：把用户问题和知识库内容放到同一个语义空间里，然后找出最相关的资料。

FastAPI 2026/4/25

引入CRUD

接口实现流程的四个步骤

  1. 模块化路由->APIRouter
  2. 定义模型类->数据库表
  3. 在crud文件夹里创建文件，封装操作数据库的方法
  4. 在路由处理函数中调用crud的方法

下面展示具体的流程

模块化路由

比如说我们有个ai模块，有个接口要到ai_chat表里查询最近与ai的会话记录

首先在routers文件夹里创建一个ai.py文件，定义一个APIRouter实例，并且添加路由处理函数，如

from fastapi import APIRouter
router = APIRouter(prefix="/api/ai", tags=["ai"])
@router.get("/ai")
async def get_session(skip: int=0,limit: int=10, db: AsyncSession=Depends(get_db)):
    result = await get_session_crud(db, skip, limit)
    return {
        "code": 200,
        "msg": "success",
        "data": result
    }

这个就相当于controller层了，负责处理请求和响应，调用crud层的方法来操作数据库。

定义模型类

在models文件夹里创建一个ai.py文件，定义一个ORM模型类来映射数据库表，如

from datetime import datetime

from sqlalchemy import DateTime, String, Text
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    created_at: Mapped[datetime] = mapped_column(
        DateTime,
        default=datetime.now,
    )


class ai(Base):
    __tablename__ = "ai_chat"
    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    user_id: Mapped[int] = mapped_column(unique=True, nullable=False, comment="用户id")
    question: Mapped[str] = mapped_column(Text, nullable=False, comment="问题")
    answer: Mapped[str] = mapped_column(Text, nullable=False, comment="回答")

注意如果在模型类中如果不映射所有的字段，那么ORM就会忽略没映射的字段

在crud文件夹里创建文件，封装操作数据库的方法

其实如果业务比较复杂，这里应该加上schema，Service，Repository等层来分离不同的职责，但这里为了简单起见，就直接在crud里封装了。

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession
from models.ai import ai


async def get_session_crud(db: AsyncSession, skip: int = 0, limit: int = 10):
    stmt = select(ai).offset(skip).limit(limit)
    result = await db.execute(stmt)
    return result.scalars().all()

这个函数就是封装了查询数据库的方法，接收一个数据库会话和分页参数，返回查询结果。

在路由处理函数中调用crud的方法

注意include到main.py里
而且router里的方法要和crud里定义的方法方法名不一样，防止和路由处理函数重名了

接入ORM
FastAPI 2026/4/25

在FastAPI中接入ORM可以让我们更方便地操作数据库，下面是一个简单的示例，使用SQLAlchemy作为ORM工具。
需要注意，SQLAlchemy包已经包含了异步模块，但是需要安装aiomysql或asyncpg等异步数据库驱动来支持异步操作。

首先安装必要的包：

pip install sqlalchemy[asyncio] aiomysql

然后配置数据库连接和会话：

from collections.abc import AsyncGenerator

from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

ASYNC_DATABASE_URL = "mysql+aiomysql://root:123456@localhost:3306/news_app?charset=utf8mb4"

# 创建异步引擎
async_engine = create_async_engine(
    ASYNC_DATABASE_URL,
    echo=True,
    pool_pre_ping=True,
)

# 创建异步会话工厂
AsyncSessionLocal = async_sessionmaker(
    bind=async_engine,
    class_=AsyncSession,
    expire_on_commit=False,
    autoflush=False,
    autocommit=False,
)


# 依赖项，用于获取数据库会话
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
        finally:
            await session.close()

在这个示例中，我们创建了一个异步数据库引擎，并定义了一个异步会话工厂。get_db函数是一个依赖项，可以在FastAPI的路由中使用，以便在请求期间获取数据库会话。

接下来，我们可以在路由中使用这个依赖项来操作数据库：

from fastapi import Depends
from sqlalchemy import select
@app.get("/items/")
async def read_items(db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Item))
    items = result.scalars().all()
    return items

在这个路由中，我们使用Depends(get_db)来获取数据库会话，并执行一个简单的查询来获取所有的Item对象。通过await db.execute()来执行查询，并使用scalars().all()来获取结果列表。

增加

先新建一个DTO类来接收请求体参数：

from pydantic import BaseModel
class ItemCreate(BaseModel):
    name: str
    description: str
    price: float

然后在路由函数中使用这个DTO类来接收请求体参数，并把它转换为ORM模型对象来进行数据库操作：

@app.post("/items/")
async def create_item(item: ItemCreate, db: AsyncSession = Depends(get_db)):
    item_obj = Item(**item.dict())
    db.add(item_obj)
    await db.commit()
    await db.refresh(item_obj)
    return item_obj

这里的item: ItemCreate表示这个参数是一个请求体参数，FastAPI会自动将请求体中的JSON数据解析成一个ItemCreate对象，并传递给create_item函数。然后我们通过item.dict()方法将DTO对象转换为一个字典，再通过**操作符将字典解包成关键字参数来创建一个ORM模型对象item_obj。最后我们将这个对象添加到数据库会话中，提交事务，并刷新对象以获取数据库生成的ID等字段，最后返回这个对象。

注意还要先定义好ORM模型类Item，并且在数据库中创建好对应的表。就是那个类定义里有__tablename__ = “items”的那个类。

FastAPI 2026/4/25

查询

先来看看简单的查询方式

from sqlalchemy import select
@app.get("/items/")
async def read_items(db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Item)).where(Item.name == "item1")
    items = result.scalars().all()
    return items

这里可以总结一下查询的一般方式：await db.execute(select(模型).where(条件))，然后通过scalars()方法把结果转换为指定对象列表，最后通过all()方法获取所有结果。

模糊查询和多条件查询

@app.get("/items/")
async def read_items(db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Item).where(Item.name.like("%item%")|Item.price > 10))
    items = result.scalars().all()
    return items

跟mysql里一样，like表示模糊查询，%表示任意字符，|表示或，&表示且。

聚合和分页

@app.get("/items/")
async def read_items(db: AsyncSession = Depends(get_db), page: int = 0, page_size: int = 10):
    result = await db.execute(select(func.count(Item.id)))
    total = result.scalar()
    skip = (page - 1) * page_size
    result = await db.execute(select(Item).offset(skip).limit(page_size))
    items = result.scalars().all()
    return {"total": total, "items": items}

yield and await

yield 是一个生成器函数的关键字，它可以暂停函数的执行，并返回一个值给调用者。当函数再次被调用时，它会从上次暂停的地方继续执行，而不是从头开始执行。可以用来惰性求值，慢慢处理大量数据，防止内存溢出。

await 是一个异步函数的关键字，它可以暂停函数的执行，等待一个异步操作完成。当异步操作完成后，函数会继续执行，而不会阻塞其他代码的执行。可以用来处理IO密集型任务，提高程序的性能。
如果调用一个异步函数不使用await，那么这个函数会返回一个协程对象，而
函数结果不一定执行完成，所以在使用异步函数时，必须使用await来等待它的结果。

**总结一下就是调用异步函数必须使用await来等待它的结果，而yield是生成器函数的关键字，可以暂停函数的执行，并返回一个值给调用者。

在路由中使用ORM

先创建一个会话工厂

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
DATABASE_URL = "mysql+aiomysql://user:password@localhost/dbname"
engine = create_engine(DATABASE_URL)
Async_SessionLocal = async_sessionmaker(autocommit=False, autoflush=False, bind=engine)

async def get_db():
    async with Async_SessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception as e:
            await session.rollback()
            raise e
        finally:
            await session.close()

这个函数会创建一个数据库会话，并在使用完后自动提交事务或回滚事务，并关闭会话。

在路由中使用这个函数来获取数据库会话：

from fastapi import Depends
@app.get("/items/")
async def read_items(db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Item))
    items = result.scalars().all()
    return items

这里的Depends(get_db)表示这个参数是一个依赖项，FastAPI会自动调用get_db函数来获取数据库会话，并将其作为参数传递给read_items函数。这样我们就可以在路由中使用ORM来操作数据库了。
