Git基本操作
Git 2026/5/21

开篇前先推荐一个适合新手学习git的网站

LearnGitBranching

git pull

默认情况下，其实pull包含了两个命令，git fetch和git merge，他的作用是获取远程分支的最新提交(fetch)并且合并到本地分支(merge)，实际开发中一般在自己的分支上 git pull origin main来合并主分支最新的提交。

其中git fetch是获取远程分支的最新情况但不合并，熟练之后我们可以先fetch检查一下代码，再手动merge。

注意本地的main分支和origin/main是两个不同的分支，当fetch origin后，你在本地main分支无法直接查看修改，需要运行git diff main origin/main 来查看远程main的最新情况。检查无误后就可以git merge origin/main 将远程的修改合并到本地了。

commit and checkout

commit是提交代码,产生一次commit指向父commit，checkout是切换分支

merge

git merge <branch> # 将branch分支合并到当前分支

那这里是什么意思呢，举个例子，日常开发中不都是在自己的分支上merge main分支吗，就是把 main 分支上的最新代码合并进你自己的分支，但不会修改 main。比如当前在member1分支执行git merge main
假如开始时候是这样：

A --- B --- C        main
      \
       D --- E      member1

执行git merge main之后(在member1分支执行)

A --- B --- C        main
      \       \
       D --- E --- M member1

那如果这时候交了个合并member1到main的pr呢

A --- B --- C  ------ G      main
      \       \      /
       D --- E --- M member1

就会变成这样，所以明白了吗，在两个分支已经分叉的情况下，merge就是将另一个分支有的，当前分支没有的提交合并到当前分支并且产生一个新的提交，并且指向两个父提交。


在fixBug上merge main

这里有一种特殊情况，假如当前分支相对于main什么都没有修改，那merge main会怎么样呢
对于下图情况，在member1分支执行merge main会怎么样？

main:    A --- B --- C --- D
              ^
member1:      B

也可以画成

A --- B --- C --- D    main
      ^
      member1

因为每个分支都有一个头指针指向当前分支的head

答案是直接将member1的头指针指向D

A --- B --- C --- D    main
                  ^
                  member1

这个就叫快速合并(fast-forward merge),很符合直觉，毕竟自己什么都没改，要合并别人新的修改直接用别人的最新版不就行了。
这个就是我们小学期小组合作的逻辑，你提交之后再拉取main，由于期间没有任何修改，你的分支的指针会直接指向main的head，你再修改再提交再合并到main在图上就是一个闭环。

merge的优势在于保留了每个merge的完整历史记录，缺点是大部分情况下merge都会多产生一个commit，如果分支较多，历史记录会变得很复杂

rebase

merge是一种会保留修改记录的合并，在多人协同开发的项目中可能会变乱，那么有没有一种不保留分叉记录的合并，使得main分支就好像是按顺序开发的一样呢？
当然是有的，那就是rebase。

git rebase <branch> # 将当前分支的commit移到branch分支的最新commit之后

rebase 可以理解成：
把你当前分支上的提交“挪到”另一个分支的最新提交后面重新排一遍。

还是刚才的例子，
git checkout member1
git rebase main
意思是把 member1 上自己新增的提交，重新接到 main 最新提交后面。
一开始是这样：

A --- B --- C        main
      \
       D --- E      member1

如果在member1上执行git rebase main
结果是

A --- B --- C        main
             \
              D' --- E'   member1

注意这里是 D’、E’，不是原来的 D、E。

因为 rebase 不是简单合并，而是：

  1. 先把 member1 上独有的提交 D、E 暂时拿下来；
  2. 把 member1 移到 main 的最新提交 C 后面；
  3. 再把 D、E 的改动重新应用一遍；
  4. 生成新的提交 D’、E’。

所以rebase后相当于

A --- B --- C --- D' --- E'   member1
            ^
            main

结果就是历史变成一条直线，看起来像你是在 main 最新代码基础上开发的。

总结

merge：保留分叉，把两条线合到一起，安全但历史可能乱。

rebase：把自己的提交重新放到 main 后面，历史干净但会改写提交。

merge：适合保留真实分支合并历史，常用于把功能分支合入 main，也可以用于把 main 同步到个人分支。

agent设计范式
agent 2026/5/19

目前，agent有三种设计范式：分别是React、Plan-and-Execute和Reflexion。

React(Reasoning and Acting)

React范式就是一个循环，每个循环由三个步骤组成，形成一个完整的Throught-Action-Observation的闭环。

  1. Thought：agent根据当前环境和上下文信息进行思考，决定action阶段要做什么。
  2. Action：agent执行上一步决定的动作，调用工具或者进行交互。
  3. Observation：agent接收action的结果，获取新的环境信息和上下文，进入下一轮循环。

为什么要把这三步分开？因为如果让模型直接行动，它可能会冲动决策，比如还没搞清楚用户到底要什么就急着调用工具，就想学生还没读懂题目就急着写答案一样。加入Thought阶段可以让模型先把问题理清楚，写出推理过程，而且这个过程是可见的，调试起来更加方便。

不过React范式有一个明显的缺点就是走一步看一步，每一步都是局部最优决策，处理非常复杂，需要全局规划的任务中，可能在中间几个子任务之间反复打转或忘了最初的目标是什么。

什么是agent
agent 2026/5/17

agent是什么

agent本质是一个能够自主完成目标的ai系统，跟llm的区别在于自主性。

传统的llm是用户问一个问题，他回答一下，每次都是独立的，被动的响应；而agent有自己独立完成任务的能力，用户给他一个复杂目标，它自己进行步骤规划，调用工具，访问记忆与感知环境来一步一步的执行，直到完成任务。

总结：agent相比llm的特性是：工具调用，记忆机制，多步推理和自我纠错

agent的核心组件

LLM

Agent的大脑，所有决策，工具调用等核心步骤都经过llm，主要用与判断下一步该做什么，怎么做

工具系统

相当于给agent提供能力的接口，agent通过调用工具来获取外部信息。
Anthropic在2024年提出了MCP，全称 Model Context Protocol，是一个让 AI 应用连接外部数据和工具的开放协议标准。

MCP 主要有三类角色：

  • Host：承载 AI 的应用，比如 Claude Desktop、Claude Code、IDE 等
  • Client：Host 内部负责和 MCP Server 通信的部分
  • Server：对外提供能力的服务，比如文件系统、数据库、搜索工具、第三方平台接口

也就是说，agent 本身不是 MCP，MCP 更像是 agent 连接外部世界的标准接口。

一个 MCP Server 最常提供三类能力：

  • Tools：给 agent 调用的函数，比如查数据库、读文件、发请求
  • Resources：提供上下文数据，比如文件内容、数据库记录、接口返回结果
  • Prompts：预定义好的提示模板，帮助组织任务流程

其中最重要的通常是 Tools，因为它直接决定 agent 能做什么。

记忆系统

agent的记忆系统可以分为短期记忆和长期记忆两种：
短期记忆：就是这轮对话的上下文，装在context window里，llm可以直接访问，适合存储当前任务相关的信息和状态。

长期记忆：通常通过向量数据库实现，把重要信息embedding后存储起来，agent可以根据需要检索相关记忆来辅助决策，适合存储跨任务、跨会话的重要信息。

规划模块

规划模块的底层依赖的是LLM的推理能力，而提升推理能力有几种主要的手段。

第一是链式思维（Chain of Thought），通过在提示里引导模型一步步推理，来提升复杂问题的解答能力。比如在 prompt 里加一句「Let’s think step by step」

第二是思维树（Tree of Thoughts），在链式思维的基础上，允许模型在推理过程中进行分叉，探索多条推理路径，最后选择最优解。比如在 prompt 里加一句「Let’s think step by step, and explore multiple reasoning paths」

有了这些推理技术打底，规划模块有两种主流模式

Plan-and-Execute(先规划后执行)

先让LLM输出一个完整的计划，然后再一步步执行这个计划。适合任务结构比较清晰，步骤明确的场景。

ReAct(边执行边规划)

每执行一步就让LLM重新评估当前状态，决定下一步该做什么。适合任务结构不确定，需要根据环境反馈动态调整的场景。

答好这道题，能把四个组件和类比（LLM 是老板、工具是技术团队、记忆是档案室、规划是项目经理）结合起来说，会非常加分。

和workflow，tool的区别

agent、workflow和tool是三个不同层次的概念。

  • tool：是一个具体的功能接口，比如一个搜索工具、一个数据库查询工具，提供特定的能力给agent调用。
  • workflow：是一个预定义的流程，规定了完成某个任务需要哪些步骤，步骤之间的顺序和条件。它更像是一个固定的剧本，agent按照这个剧本来执行。
  • agent：是一个具有自主决策能力的系统，能够根据目标和环境动态规划和执行任务。它可以调用工具，也可以按照workflow执行，但它不受限于固定的流程，可以根据实际情况灵活调整。

Anthropic 在他们的 Agent 工程实践中总结了几种常见的 Workflow 编排模式，值得了解一下。
第一种叫「Prompt Chaining」（提示链），就是把一个大任务拆成多个小步骤，前一步的输出作为后一步的输入，像流水线一样串起来。
第二种叫「Routing」（路由），先用一个 LLM 做分类判断，然后根据分类结果把请求分发到不同的处理分支，前面客服系统的例子就是典型的路由模式。
第三种叫「Parallelization」（并行化），把可以同时进行的子任务并行执行，最后汇总结果，这在需要多维度分析的场景下特别有用，比如同时从多个数据源检索信息。
第四种叫「Orchestrator-Workers」（编排者-工人），一个中央编排者负责分配任务，多个 Worker 各自完成子任务，适合任务可以分解但子任务之间相互独立的场景。

总的来说，agent和workflow不是互斥的，在生产中agent太难控制，workflow又太死板，所以最好用workflow固定主流程框架，在需要灵活判断的节点嵌入agent做决策。

这个 Lua 脚本主要做四件事。
第一，先根据 voucherId 组装 Redis key，一个是库存 key，一个是下单记录 key。
第二，读取库存，如果库存小于等于 0，就直接返回失败，表示库存不足。
第三，检查当前用户是否已经在这个券对应的下单用户集合里，如果已经存在，就返回失败，表示重复下单。
第四，如果前两步都通过，就在 Redis 里先执行库存预扣减，再把 userId 写入这个券对应的下单用户集合里，表示这个用户已经占到了购买资格。整个过程放在 Lua 里执行，是为了保证这几步操作的原子性，避免高并发下出现超卖或者一人多单。

“正常消费者第一次消费失败时，我会先 NACK + requeue=true，允许消息再消费一次。
如果第二次还是失败，就先记录一条 PENDING 状态的死信日志，然后 basicReject(requeue=false)，让消息自动进入死信队列。

如果还没成功，就再尝试补单一次，也就是重新走数据库侧的下单逻辑；如果这次补单成功，就标记成 RETRIED_SUCCESS。
如果补单还是失败，就继续执行 Redis 预占回滚，把之前 Lua 里预扣的库存和用户资格释放掉；如果回滚成功，就标记成 ROLLED_BACK。

所以这条死信链路的核心目标是让失败消息具备可追踪、可补偿、可兜底的闭环能力。”

所以结论不是 ZSet 完全不占内存，而是对于我这个‘小窗口、低阈值、及时清理、带过期时间’的限流场景，它的内存开销是可控的。”

“因为这个限流主要是为了拦截单个用户在极短时间内的重复请求，所以我按用户维度做限流，而不是做全局限流。

RAG基础
RAG 2026/4/28

RAG是什么

RAG（Retrieval-Augmented Generation）是一种结合了检索和生成的自然语言处理技术。

RAG的工作流程

RAG主要干两件事情，离线建库和在线问答

离线建库: 把资料变成可检索知识库

原始文档
↓
文档清洗/解析
↓
切分成 chunks
↓
生成向量 embeddings
↓
存入向量数据库/检索索引

常见步骤：

收集数据
例如 PDF、网页、Word、数据库记录、内部文档、FAQ 等。

解析和清洗
去掉无关内容，提取正文、标题、表格、元数据等。

切分文本
把长文档切成较小片段，比如每段 300 到 1000 tokens。
切太大，检索不精准；切太小，上下文不完整。

向量化
用 embedding 模型把每个文本片段转成向量。

建立索引
把文本片段、向量、来源信息一起存到向量数据库，比如 FAISS、Milvus、 等。

在线问答：用户提问时检索相关资料塞入prompt再调用llm回答

用户问题
↓
问题向量化
↓
检索相关 chunks
↓
可选：重排序 rerank
↓
把检索结果塞进 prompt
↓
LLM 生成答案
↓
返回答案 + 引用来源

常见步骤：

用户输入问题

对问题做 embedding
把问题也转成向量。

相似度检索
在向量库里找最相近的文档片段。

重排序
可选，用 reranker 模型把候选结果重新排序，提高相关性。

构造 Prompt
把检索到的资料作为上下文，连同用户问题一起发给大模型。

生成答案
大模型基于检索内容回答，而不是只靠自己记忆。

返回引用
最好附上来源文档、页码、URL 或 chunk ID，方便用户验证。

RAG的作用

RAG = 先从知识库里找资料，再让大模型基于这些资料回答问题。
rag的核心价值是：让模型能使用外部知识、减少幻觉、支持私有数据、并且知识库可以持续更新。

向量与向量夹角的余弦

上过高中应该都知道向量是什么，向量是有大小和方向的量，可以用来表示空间中的点、线、面等几何对象，也可以用来表示物理量如速度、力等。

在rag里，向量可以理解为文本的语义坐标。比如两句话：

苹果手机怎么截图？
iPhone 如何截屏？
字面不完全一样，但意思很接近。Embedding 模型会把它们转成一串数字，例如：

[0.12, -0.03, 0.88, 0.41, …]
这串数字就是向量 embedding。真正的 embedding 通常有几百到几千维。

向量的基本概念

在 RAG 中，向量主要用于表示语义：

文本 chunk → embedding 模型 → 向量
用户问题 → embedding 模型 → 向量
然后系统比较“问题向量”和“文档片段向量”之间的距离或相似度，找出最相关的内容。

可以把向量想象成地图上的点：

意思相近的文本 → 在向量空间里距离近
意思无关的文本 → 在向量空间里距离远
例如：

“如何重置密码”
“忘记密码怎么办”
向量会比较接近。

而：

“如何重置密码”
“北京明天天气”
向量就会比较远。

余弦相似度

余弦相似度用来衡量两个向量的“方向是否接近”。

它不太关心向量有多长，更关心两个向量指向的方向是不是一致。

公式是：

cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)
其中：

A · B 表示两个向量的点积
||A|| 表示向量 A 的长度
||B|| 表示向量 B 的长度
结果通常在 -1 到 1 之间：

1 表示方向完全相同，语义非常接近
0 表示基本无关
-1 表示方向完全相反

这其实就是高中立体几何里向量夹角余弦公式，一般拿来求二面角或异面直线夹角
在很多文本 embedding 场景里，实际常见结果更多是 0 到 1 附近。

举个二维小例子

假设有两个向量：

A = [1, 2]
B = [2, 4]
先算点积：

A · B = 1×2 + 2×4 = 10
再算长度：

||A|| = sqrt(1² + 2²) = sqrt(5)
||B|| = sqrt(2² + 4²) = sqrt(20)
代入公式：

cos(A, B) = 10 / (sqrt(5) × sqrt(20))
= 10 / 10
= 1
所以它们方向完全一致，相似度是 1。

虽然 B 比 A 长，但他们是平行向量，方向一样，所以余弦相似度认为它们非常相似。
RAG 检索时大概是这样：

用户问题：怎么修改登录密码？
↓
转成问题向量 Q
↓
拿 Q 和知识库中每个 chunk 的向量比较
↓
用余弦相似度排序
↓
取 top-k 个最相似的 chunk
↓
交给大模型生成答案

总结

向量 = 文本语义的数字表达
余弦相似度 = 判断两个语义向量方向有多接近的方法
在 RAG 中，它们共同完成的事情是：把用户问题和知识库内容放到同一个语义空间里，然后找出最相关的资料。
